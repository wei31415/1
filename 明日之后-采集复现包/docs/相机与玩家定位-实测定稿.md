# 相机与玩家定位 · 实测定稿

> 本文记录**已经实测跑通**的定位配方，官方包与 vivo 渠道包都验证通过。
> 对应脚本：`scripts/camfind6.js`。所有判据都来自实测数据，不是推测。

---

## 0. 一句话

```
背靠背两次转储 → 求"位移向量出现次数最多"的那一簇 → 得到走路方位角 θ
→ 在场景区域里搜"正交归一 3×3 + base+48 是 w=1.0 位置 + 某行水平方位角 ≈ θ"
→ 再用"B 转储里同一偏移的位置位移必须等于该簇位移"复核
→ 命中的就是相机；yaw = atan2(r2.x, r2.z)，pitch = asin(r2.y)
```

**不需要 ±180 修正，不需要灵敏度标定常数，不需要失败重试凑。**

---

## 1. 完整步骤

### 步骤 1：背靠背两次转储

```bash
# A 转储
dd if=/proc/<pid>/mem bs=65536 skip=<块号> count=<块数>   # 场景区域
# 按住 W 800ms（一次就好）
# B 转储（紧接着，中间不要碰鼠标、不要隔时间）
```

**这条是硬要求。** 早期把"转储"和"走路探针"隔了 10 分钟，中间人转过视角，
结果算出 175° 的假差异，差点得出"引擎存的是 -Forward"的错误结论。
背靠背之后差异直接降到 0.03°。

### 步骤 2：求主位移簇，得到 θ 和玩家位置

把 A、B 里**同 id** 的节点配对，算位移向量 Δ，**按 1 单位取整分组，取数量最多的一簇**。

```js
const groups = new Map();
for (const b of nB) {
  const a = mapA.get(b.id);
  if (!a) continue;
  const dp = [b.p[0]-a.p[0], b.p[1]-a.p[1], b.p[2]-a.p[2]];
  if (Math.hypot(...dp) < 12) continue;
  const k = dp.map(v => Math.round(v)).join(',');
  if (!groups.has(k)) groups.set(k, []);
  groups.get(k).push({ a, b, dp });
}
const D = [...groups.values()].sort((x, y) => y.length - x.length)[0][0].dp;
const theta = Math.atan2(D[0], D[2]) * 180 / Math.PI;      // ★ 相机/走路方位角
```

**为什么必须是"最大簇"而不是"位移最大的节点"：**
玩家位移在内存里会出现在**上百份副本**里（官方包实测 207 份）。
而"位移最大的单个人形节点"往往是遍地都是的小物件在抖动 —— 实测挑出过
位移 106.9 的垃圾节点、位移 45.9 的干扰节点，全都不是玩家。

### 步骤 3：定向搜索相机矩阵

对场景区域缓冲区里**每个 4 字节对齐的偏移**做下面全部检查：

| 检查 | 条件 | 依据 |
|---|---|---|
| 位置存在 | `float @ off+60 == 1.0`（w） | 位置是 float4，w 恒为 1 |
| 位置合理 | `|x| ≥ 100 && |z| ≥ 100` | 世界坐标不会贴着原点 |
| 三行归一 | `|r0| = |r1| = |r2| = 1`（±0.01） | 旋转矩阵 |
| 两两正交 | `r0·r1`, `r0·r2`, `r1·r2` 绝对值 < 0.01 | 旋转矩阵 |
| **方位角匹配** | 三行中某一行水平投影 `(x,z)` 的方位角与 `θ` 相差 **< 3°**（θ 与 θ+180 两个方向都试） | 相机在走动时会自动摆到角色正后方，所以相机 forward 的方位角就是 θ |
| 距离合理 | 位置距主位移簇中心 **5~300 单位** | 相机长在玩家身上 |

> 注意：**不要**加 `|v.y| > 0.03` 之类的俯仰过滤。平视时 forward 的 y 分量只有
> `sin(-0.71°) = -0.012`，一加这条就是 0 命中。俯仰靠"正交归一 + 方位角"就够了。

### 步骤 4：位移复核（决定性的一步）

对上一步的每个候选，去 **B 转储的同一偏移**读位置，要求：

```
B.pos − A.pos  ==  Δ*      （实测差值 0.00）
```

这一步把同源副本全部锁死，也能排除掉"碰巧方位角对上"的静态矩阵。

### 步骤 5：读朝向

```
r1  = float3 @ off+16     // up
r2  = float3 @ off+32     // forward
yaw   = atan2(r2.x, r2.z) * 180/π
pitch = asin(r2.y)        * 180/π      正 = 抬头
```

## 3. 曾经走错的三条路（记下来别再走）

| 路子 | 为什么不行 | 实证 |
|---|---|---|
| 节点配对：相机节点 = 包围盒 200000 的无限盒，且与相机矩阵位置重合 | 官方包只有 1~2 个无限盒，vivo 包有 **40 多个**，位置撒满地图（`(-37993,-14567)`、`(38400,9600)`…），不再唯一 | 在 40 多个无限盒节点附近各扫 ±0x400 找矩阵，命中矩阵的 pos **全部等于该节点自身位置**，说明是物体自己的变换 |
| 鼠标转视角 + 线性度（80px vs 320px 应 1:4） | 确实能唯一命中（1065 个里只有 1 个），但那个矩阵 **pos 是死的**（走 2.2 秒位移 0.0），只含朝向不含位置 | off 0x2773e40 只转不动；`pos` 恒定 |
| 按"人形三围"挑玩家节点 | 这种小物件遍地都是，位移最大的那个往往是垃圾 | 挑中过 0x795d（位移 106.9）、0x7ba5（位移 45.9），都不是玩家 |

## 4. vivo 包与官方包的差异（会影响瞄准参数）

| 项目 | 官方包 | vivo 包 | 影响 |
|---|---|---|---|
| 鼠标灵敏度 | 3.7 像素/度 | **约 6~12 像素/度，且非线性** | 必须闭环反馈，不能算死像素 |
| `+dx` 对 yaw | 增大 | **减小**（符号相反） | 注入方向要取负 |
| 玩家相对相机 | 相机 + forward×32 | **相机 − forward×32** | `getPlayerAndCam()` 里的 `px/pz` 预测点在 vivo 包上是反的，只能当兜底 |
| 相机↔玩家距离 | 36.0 单位 | 32.1 单位 | 只影响距离阈值，不影响方向 |
| 俯仰钳位 | 约 ±23° | 约 ±23°（同引擎） | 贴太近会瞄不到，站位要保持 0.6~2.0 米 |

## 5. 用法

```powershell
# 每次启动游戏 / 换图后跑一次，直接写 session.json
node scripts\camfind6.js
```

输出里会打印：主位移簇、θ、候选数、复核通过的个数、最终相机偏移与 yaw/pitch。
脚本只在"方位角 + 位移复核"都通过时才写 `session.json`，不会写半成品。

## 6. 已知遗留

1. **vivo 包里"玩家节点"识别偏弱**：`playerNodeId()` 找不到无限盒锚点时退化成
   "距相机 32~66 单位的人形节点"，而真实玩家正好在 32.1 单位的边界上，可能认错。
   后果是站位判据和射线里的"排除玩家自身"会失准。
2. **白名单巡回里有 3/8 个点"准心没咬住"**：节点都在、站位也对，就是射线不穿。
   待查方向：俯仰钳位 ±23°、或玩家节点认错导致射线被自身遮挡。
3. **站位判据（点到包围盒距离）在包围盒膨胀时会算成 0**，日志里那些"在盒子里"就是它。
